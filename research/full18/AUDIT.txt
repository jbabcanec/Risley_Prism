SOURCE AND IMPLEMENTATION CAVEATS

The five recorded original hashes (core.py, model.py, separable.py, solve.py,
fmodel.py) independently match current files. Every combined output also has
the same poc3.py hash, matching current poc3.py. These facts support exactly
those files. They do not hash the whole repository or every wrapper/dependency.

verify_results.py silently skips result files with no theta/parameters/x18.
This did not affect these two ten-row reports, but future rates must use the
number of attempted inputs, not just the evaluator's returned-row denominator.

Small rigor gap: profile_observation.point_check and verify_results evaluate
abs(fm-y)+fr using ordinary NumPy rounding at the last subtraction and sum.
An outward-rounded final expression should be used before calling that scalar
a formal upper bound. The displayed pair has ample slack, so an ordinary ulp
correction cannot change its conclusion. Existing fmodel point calls use the
stored binary64 sampling clock; distinguish that from the independent strict
verifier's exact k/20 clock. Neither issue changes the constructed strict
witness argument, which uses the separate interval verifier.

Minor documentation issue: verify_pairs.py imports NAMES/LO/HI from
profile_pairs.py, which imports scipy.optimize at module load. Its statement
that no optimizer is imported is literally inaccurate; no optimizer is called
by the independent verification path, and its optical equations are separate.

No material count or common-record-witness error was found. The main risks are
conflating candidate compatibility with parameter accuracy, mixing identically
named cases across datasets, presenting adaptive repairs as frozen-policy
successes, or promoting finite tested noise patterns to universal guarantees.
